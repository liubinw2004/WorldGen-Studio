# 全景视频：用已有点云做真实几何渲染

你在 `/world` 左侧面板点「生成全景视频」，得到的是一个 **2:1 等距柱状（equirectangular）MP4**，可以直接在浏览器里用内翻球面播放、拖动环视、下载分享。

**先说清楚一件事：这不是 AI 生成的视频。**

每一帧都是把该场景已有的高斯点云（`outputs/studio/<scene_id>/splat.ply`，52 万～210 万点）逐帧投影成全景图，再编码成 H.264。所以它没有"想象"出来的内容——没有点的地方就是空的；但它有**真实几何、真实视差、零显存占用、秒级产出**。

---

## 1. 为什么不接文生视频模型

三个独立的原因，任何一个都足够否掉：

1. **显存**。本机 RTX 3080 Ti **12 GB**。Wan 2.x / CogVideoX 这一档要 16～24 GB 才好跑，12 GB 必须上量化，单场景生成 10 分钟起。
2. **形态不对**。文生视频模型产出的是**透视（perspective）画面**，不是 360 全景。要做成全景得逐段生成再拼接，接缝和视差都对不上；这恰恰是本项目最不该丢的东西。
3. **几何是现成的**。管线已经产出了带深度的高斯点云，把它重新投影一遍就能得到任意机位的全景画面，为什么要让模型去猜？

补充一个实测数字说明"让模型猜"有多不可靠：单个场景的中位深度只有 **1.52 m**，往前一步（1.0 m）就有 **57%** 的画面变成空洞（见 `docs/world.md`）。这是单张全景的几何上限，模型补不出来。

## 2. 运镜（`path` 参数）

| `path` | 界面名 | 机位 | 是否重投影 | 速度 |
|---|---|---|---|---|
| `still` | 静止 | 不动，只有昼夜与风 | 否（缓存直出） | 最快 |
| `orbit` | 环绕 | 偏航转一整圈，首尾帧相接可无缝循环 | 否（整数列平移） | 快 |
| `handheld` | 手持 | 两组低频正弦抖动，加呼吸感 | 否（整数列/行平移） | 快 |
| `dolly` | 推近 | 沿 +z 推进 `0 → 0.4 m → 0`，产生视差 | **是** | 较慢 |
| `crane` | 升起 | 垂直起降 `0 → 0.4 m → 0` | **是** | 较慢 |

### 为什么平移上限是 0.8 m

点云是从**一个视点**拍到的球壳。机位一走开，原本被近处几何挡住的地方没有任何点，画面就出现空洞。实测覆盖：

| 平移 | 覆盖率 |
|---|---|
| 0 m | 100% |
| 0.5 m | 59.0% |
| **1.0 m** | **43.3%** |

所以代码里 `DOLLY_MAX_M = 0.8` 是**硬上限**，任何调用方都不可能超过它。

### 为什么出厂只走 0.4 m

点云在投影像平面上是**规则等距柱状栅格**（原始全景 1024×512 一个像素一个高斯点）。一旦机位平移，就等于对这个栅格做重采样；位移越接近采样间距，混叠条纹（同心摩尔纹）越明显——`_probe/splat_render.py` 里记录过同一现象。实测水面区域的高频能量相对静止帧的比值：

| 位移 | 高频能量比 |
|---|---|
| 0.2 m | 1.8× |
| **0.4 m** | **2.4×** |
| 0.5 m | 3.1× |
| 0.6 m | 4.1× |
| 0.8 m | 7.2× |

0.4 m 是仍然"干净"的最大位移（同时也是中位场景深度 1.52 m 的 26%，视差看得出来）。想要更大视差可以传 `travel`：取值范围 0~0.8 米，**超出会被拒绝并返回 400**（不会静默夹取）。

### 为什么 dolly/crane 是"推进再回落"

播放器是 `loop = true` 的。单向推到底再跳回起点是一个硬切；用 `0.5 - 0.5·cos(2πt)` 缓入缓出，首尾帧机位重合，循环时看不出接缝。`orbit` 同理（偏航整一圈），`handheld` 则用了整数倍于时长的频率。

## 3. 性能

### 3.1 设计期实测（512 K 点，2048×1024 单帧）

| 做法 | 耗时 |
|---|---|
| 朴素：每帧重算投影 + `argsort` + 5 次 disc 散写 | **476 ms** |
| 预计算 + 纯偏航（整数平移 `u = (u0 + du) % W`） | **71 ms** |
| 逐帧色调变换（52 万点 × 3 float） | 9 ms |

结论只有一条：**必须做场景级预计算**。加载 PLY 后一次性算好并按深度从远到近排好序的 `centers / rgb_float / depth / u0 / v0 / lum / lift / phase` 会被缓存复用（按 `(scene_id, W, H)`，最多 2 份）；纯旋转运镜于是退化成整数列平移，既不重算三角函数也不重排深度。

### 3.2 本实现实测（同场景，每个运镜取 6 帧平均，含逐帧色调变换与风）

| 分辨率 | 运镜 | 单帧 | disc 采样数 |
|---|---|---|---|
| 1024×512 | still / orbit / handheld | 111 ms | 5 |
| 1024×512 | dolly / crane | 153 ms | 5 |
| 2048×1024 | still / orbit / handheld | 271 ms | 13 |
| 2048×1024 | dolly / crane | 296 ms | 13 |

其中**逐帧色调变换实测约 48 ms**（比设计期估的 9 ms 高，原因是每帧要新建若干 52 万 × 3 的浮点临时数组）。恒定光照的片子会命中 memo，省掉这一项。

### 3.3 整片耗时（含编码）

| 片子 | 采样 | 渲染+编码耗时 | 文件 |
|---|---|---|---|
| 静止 · 4 s · 1024×512 · 24 fps（光照恒定） | 96 帧 | **6.5 s**（~68 ms/帧） | 1.21 MB |
| 静止 · 4 s · 1024×512 · 24 fps（0.9→0.2 昼夜过渡） | 96 帧 | **11.6 s**（~120 ms/帧） | 1.31 MB |
| 推近 · 2 s · 2048×1024 · 24 fps（0.85→0.25） | 48 帧 | **17.0 s**（~354 ms/帧） | 6.29 MB |

散点用 disc 半径（1024 宽取 1.0 → 5 个采样点；2048 宽取 2.0 → 13 个），之后再用 1 遍 3×3 邻域把 1 px 缝隙补上。

## 4. 昼夜与风

在 Python 端复刻 `app/static/world.js` 里着色器的色调逻辑，保证视频和实时漫游看着是同一个世界：

- 归一化亮度 `lum = rgb·(0.299, 0.587, 0.114) / 255`
- 夜晚偏蓝 `(0.52, 0.66, 1.10)` ↔ 白天近白 `(1.05, 1.03, 0.97)`，按 `smoothstep(0, 0.85, light)` 插值
- 亮度高的点（灯笼、亮窗）天黑后保留暖金辉光 `(1.22, 1.02, 0.76)`，权重 `smoothstep(0.42, 0.95, lum) × (1 - light) × 0.85`
- 整体再乘 `0.92 + 0.10 × light`

**风**用屏幕空间抖动近似，不重算世界坐标：每个点预计算一个随机 `phase`，每帧 `u += round(A·sin(ωt + phase)·lift)`，`lift` 按高度加权，所以只有树冠和灯笼会动。振幅随输出宽度缩放（1024 宽时最大 ±2 px）。

`light` 支持固定值和「起始→结束」过渡（面板上的「昼夜过渡」开关就是 `0.9 → 0.2`）。

## 5. 参数

### HTTP API

```
POST /api/world/video
{
  "scene":     "20261021-...-koi-pond-war",   // 必填，必须已存在 splat.ply
  "path":      "still",        // still | orbit | handheld | dolly | crane
  "seconds":   6,              // 1 ~ 20
  "fps":       24,             // 12 ~ 30
  "width":     1024,           // 1024 | 2048
  "height":    512,            // 省略则 width/2；必须满足 2:1
  "light_from": 0.9,           // 0 ~ 1；与 light_to 都不传时默认 0.9
  "light_to":   0.2,           // 省略则等于 light_from；之间做昼夜渐变
  "wind":      0.6,            // 0 ~ 1（true/false 也接受），非数字返回 400
  "travel":    0.4             // 可选，dolly/crane 平移量，0 ~ 0.8 米
}
→ { "ok": true, "job": "<id>", "frames_total": 144 }
```

参数不合法一律 400 + `{"ok": false, "error": "..."}`；已有任务在跑返回 409。

> **光照默认值**：`light_from` 与 `light_to` **都不传**时按产品默认做昼夜渐变 `0.9 → 0.2`（和界面上「昼夜过渡」默认开启一致），不再是一段几乎静止的片子。只传 `light_from` 则保持恒定光照，想要真正的静止画面就显式传 `light_from = light_to`。
>
> `travel` 超出 `0~0.8` 米会**被拒绝并返回 400**，不会静默夹取。

| 接口 | 用途 |
|---|---|
| `GET /api/world/video/<job_id>` | `{state: running\|done\|error\|cancelled, progress, frames_done, frames_total, url, bytes, error}` |
| `POST /api/world/video/<job_id>/cancel` | 置取消标志，下一帧边界退出并删掉半成品 |
| `GET /api/world/videos` | 已生成列表（新到旧）。**只收录写完 sidecar 的成品**，渲染中/被 kill 的半成品不会出现 |
| `GET /api/world/video-file/<name>` | 取 MP4（`.mp4` 白名单 + 正则校验防穿越，支持 Range） |

任务状态是**进程内字典**（本地单用户工具，不引数据库），完成 10 分钟后清状态、**保留文件**。同时只允许 1 个渲染任务——渲染是 numpy 密集运算会长时间持有 GIL，一旦并发，前端轮询就会卡住。渲染循环里每帧 `time.sleep(0)` 让出 GIL，也是同一个原因。

### 产物

```
outputs/videos/<scene_id 前 40 字符>-<path>-<YYYYmmdd-HHMMSS>.mp4
outputs/videos/<同名>.json      # 场景、运镜、时长、帧率、分辨率、耗时、点数
```

### 模块内直接调用

```python
import pano_video
pano_video.generate_video(

    {"path": "orbit", "seconds": 8, "fps": 24, "width": 2048, "height": 1024,

    progress_cb=lambda done, total: print(done, total),
    cancel_flag=lambda: False,
)
```

## 6. 依赖

**PyAV**（`av >= 13.0.0`，实测 19.0.2）。

- PyAV **自带 ffmpeg 和 libx264**，系统里**不需要**另装 ffmpeg，也不需要 `ffmpeg.exe` 在 PATH 里。
- `av` 是**函数内 import** 的：缺包时 `import app.pano_video` 和整个 server 都能正常启动，只有点「生成」时报一条带安装命令的错误。
- 编码参数：H.264 / `avc1` / `yuv420p` / `+faststart` / `crf 20` / `preset veryfast`。这四样是浏览器 `<video>` 和 `THREE.VideoTexture` 能直接播的前提；`+faststart` 是 **container** 选项，不是 codec 选项。
- 宽高必须是偶数（`yuv420p` 要求），且 `W = 2 × H`。

## 7. 已知限制

- **点数 > 300 万直接拒绝**并报出实际点数（Python 端 OOM 风险）。当前最大场景约 210 万点。
- **dolly / crane 有混叠条纹**。这是重采样规则栅格的必然结果，不是 bug。缓解手段只有限制位移（见 §2）。真正的解法是补点或做 inpainting，本工具不做。
- **2048×1024 在低点数场景会显得糊**：52 万点铺到 210 万像素上，一个点要负责 4 个像素，靠 disc 采样和 3×3 补洞糊过去。
- **没有音频**、没有转场、不支持自定义相机路径（只有 5 个预设）。
- 视频文件不会自动清理，需要手动删 `outputs/videos/`。启动时会扫一次该目录，把**没有同名 sidecar 的 `.mp4`** 删掉（进程被 kill 留下的半成品）；这只发生在启动时，不会误删正在写入的文件。
